# F5 内存门槛复核（2026-10-13，英国16:44）

## 结论

105GiB是排程的保守常数，不是F5实际内存需求的测量值，也没有可复核的原拟合公式。已有实测支持F5全流程峰值约55–65GiB的若干外推情形；当前可用82.11–82.46GiB，从静态容量看有运行可能。但该区间不是置信区间或上界，约2.5GiB的额外缓冲不足以覆盖已观测到的共享主机波动，因此目前不能确认“按原脚本降低门槛后即可安全完成”。本轮仅核对和记录，105GiB门槛、原队列、源码和求解参数均未修改，F5未启动。

## 105GiB的来源与更正

`scripts/run_flex_server_series.py:35` 自aef0cb7起直接写入 `required = (105 if hours > 744 else 43 if hours > 168 else 27) * 2**30`。脚本说明保留15GiB，因此105可分解为隐含90GiB工作预算加15GiB余量，但代码没有计算90的公式。初始REVIEW只引用历史744h Base约22.4GiB并列出三档，没有记录时长倍率或置信依据。该记录不足，不能将“105GiB”描述成F5已证实的最低需求；本次据实纠正，旧记录保留。

## 三种可复算外推情形

设h=2016/744=2.709677419，F1/F4的RSS分别20.144886/3.775208GiB。

| 假设 | F5预测峰值GiB | 加15GiB保留后的需求GiB |
|---|---:|---:|
| RSS随小时线性：20.144886×h |54.586143|69.586143|
| 两点RSS幂律：alpha=ln(20.144886/3.775208)/ln(744/168)=1.125274 |61.846614|76.846614|

第三项是敏感性假设，不是经校准的内存分项模型。只有两个时长，不能估计可靠置信带，也不能排除2016h排序/分解填充进一步跳升。F4/F1峰值可能发生在不同阶段；同起点但F5横跨更多季节，柔性活动行结构也会变。原始模型规模两点仿射投影约1025万变量、1246万约束、1.159e8非零元，仅供规模参考，未经2016h构建验证，不能转换成已确认的RSS。

## 当前资源与安全余量

15:43:46–15:44:16UTC（英国16:43:46–16:44:16）三次采样MemAvailable为82.463562、82.322388、82.111111GiB；应看可回收缓存后的MemAvailable，而不是约11GiB的MemFree。总RAM约123.07GiB。swap已用2.546GiB，30秒窗口内swap-in/out累计计数不变；这不能证明数小时无换页风险，也不把swap当所需RAM余量。

以最低82.111111GiB计，扣除15GiB保留后可用67.111111GiB；对64.602615GiB外推只余2.508495GiB额外缓冲，约3.9%。与旧11:23快照63.625GiB相比，当前资源改善明显，旧快照已不能作为当前资源不足的全部依据。

但共享主机的可用资源并非固定：F3运行中`MemAvailable + 本实验RSS`在47.892841–72.327667GiB间变化，跨度24.434826GiB。该和数只是扣除本实验影响的粗略代理，含缓存/内核记账变化，不能精确归因其他用户进程；至少说明运行期有效余量可明显变化。短期82GiB不是稳定预留。

原诊断脚本只在optimize回调中、间隔超过5秒时检查15GiB保留；构建、归档和导出阶段没有同等保护，2秒采样队列本身只记录RSS不执行限制，参数回读SoftMemLimit=Infinity。因此原保护不是全流程硬内存上限，不能据此保证即使预测偏低也可完整安全退出。

## 可审查的下一步（本轮不执行）

若作者决定推进F5，建议在新的独立诊断目录准备覆盖构建/预处理/排序分解/导出的资源保护和保全方案，先取得2016h实际矩阵及factor规模，再决定是否继续完整求解；同时确认运行期间能维持的主机余量。单纯把105改成某个更低常数，不能补齐这些证据。若不增加保护，应等资源更宽裕/更稳定，而不是将55–65GiB外推范围当安全上界。内存是否可运行与残差增长第3情形是两个问题，本复核不改数值判据。
